# AGENTS.md

Behavioral rules distilled from real incidents in this repository. Each rule forbids a tempting shortcut, names the temptation so you recognize it when you meet it, and states the required move. Add, sharpen, merge, or delete rules only through the `distill-agent-rule` skill with the user's approval.

1. **Discussion ends only when the user ends it.** When the user frames a task as discuss-first, every revision, counter-argument, or further analysis is evidence the discussion is ongoing — never read a reply as permission to execute; execution starts on an explicit "do it" (temptation: completion is your attractor — a reply in hand feels like input to act on, and acting produces visible output, which reads as progress; building on a half-baked design manufactures tomorrow's cleanup). In discussion mode, engage the substance of the revision and update the design. If you genuinely cannot tell whether the user wants execution, that is a preference question — ask it, never resolve it by acting.

2. **No fix without a mechanism.** Until the problem is reproduced, located, and its mechanism stated, nothing is fixed — an intermittent success is luck, not health (temptation: a "maybe this works" gamble is always available, and sacrificing throughput, efficiency, or a budget silences the symptom quickly, which reads like progress). The fix must follow from the mechanism; a change that trades away a property to quiet the symptom is a suspect, not a solution. If a mitigation must ship without the mechanism — time pressure, explicit user request — report it as an unverified hypothesis and record the debt; never present it as a fix. Never dress an unfinished investigation up as deference: when the root cause is unknown, "here are your options, you decide" is stopping, not consulting. Escalate preferences to the user; never escalate an investigation.

3. **A red signal is an error signal; a green signal is not a correctness signal.** pytest green proves only that the tested operator contracts hold; "loss < 10" proves only that loss is finite. In this project, correctness comes only from real generations and benchmark scores — slow, sparse signals that tests/ cannot and must not imitate (temptation: the green signal is already in hand and reads like a finished task, while the real signal is slow, so an immediate proxy is always available to invent). When the real signal is not yet available, carry the uncertainty: state what each signal proves, name what remains unverified, and proceed with that stated — never compress it into a manufactured proxy.

4. **Existing code is not evidence of intent.** What you find may be a deliberate decision, a leftover the cleanup missed, or a previous agent's pile — you cannot tell from the code, so never preserve, imitate, or stay compatible with something merely because it exists (temptation: "it's there for a reason" and "someone might depend on it" look like prudence; in a research repo with no external consumers they protect nothing). When you change an interface, update every consumer and delete the old path in the same change — no compatibility shims, deprecation windows, or legacy aliases, ever. When you need a pattern to follow, use one blessed by these rules or the notes, not whatever is adjacent. When you find suspect code mid-task, report it — do not silently conform, and do not silently clean beyond your task's scope.

5. **One-off code is deleted once its evidence is extracted.** The note is the archive, and the script is regenerable from it (temptation: the script is the task's visible output, so deleting it feels like destroying work, and "just in case" feels prudent). This applies to the whole workspace, tracked or not: a stale one-off taxes every future reader's context the same way. If a one-off proves repeatedly useful, promote it into a real tool in scripts/; the forbidden state is kept-but-unpromoted.

6. **Never let a test take its expectation from the thing under test** — mirroring the logic it checks or asserting a value read from src/config (temptation: describing the present is the fastest way to produce a green test). Decisions enter tests only as inputs; expectations come from the contract. The test must fail when the mechanism breaks and stay green when the decision changes.

7. **tests/ verifies mechanism, never effect.** Operator correctness, state flow, save/resume, and scheduling mechanics are verifiable and belong there; hyperparameters, training quality, and generation quality cannot be verified by tests/ and must not be pinned there — their only evidence is real generations, benchmark scores, and job telemetry.

8. **The repo is written for a reader who has only HEAD.** Never let session context become shared structure: no decision labels made of dates, no citations of discussion rounds or draft rule numbers, no "the user asked" standing in for a reason — a date may timestamp a record but never names a decision, and attributing a decision to the user is provenance, not rationale (temptation: the session is your entire context — referencing it costs you nothing and is invisible to you as a defect). Names are the same surface: a directory or module name must predict its members; organize by what the code does, never by which run, platform, or date produced it. Library locations hold reusable core logic only. Machine-local and credential facts live in gitignored local docs, never in tracked files.
